Three things this measurement does not show. The baseline is uniform-random placement, not a language model. It establishes that these constraints are hard to satisfy by chance; it does not establish that the placer beats an LLM, and no real LLM has been benchmarked. "Batches fully valid" counts a trial where every request was refused as vacuously clean, so read it alongside the 19.1% refusal rate rather than on its own. Latency is order-of-magnitude only: the mean varied 6.06 to 1.15 to 1.21 ms across three consecutive runs as the JIT warmed up, though every count-based metric was byte-identical across those runs.
Reproducibility status. The constraint solver itself is in the repository, including clearance handling (packages/ai/src/solver.ts, DEFAULT_CLEARANCE, needsFrontClearance). The measurement harness that produced the table above is not yet in the public repository and must be pushed before these figures can be independently reproduced.

How the sun engine was validated

The poster claims Lumos tracks NOAA's reference algorithm to within 0.219 degrees. Here is exactly how that number was produced.

What was compared

Lumos derives sun position from suncalc@1.9.0, called in packages/core/src/sunlight.ts. NOAA's Solar Position Algorithm was re-implemented from the published equations in a standalone script that shares no code with the application. The two were then compared on the quantity the renderer actually consumes: the sun direction vector, after Lumos applies its own azimuth-to-bearing conversion.

Self-check before trusting the result

The NOAA implementation is verified against two analytic values before any comparison runs. At solar noon on the June solstice, New York should reach 90 − 40.71 + 23.44 = 72.7°; the script computes 72.724°. At the March equinox, Singapore should reach 90 − 1.35 = 88.6°; the script computes 88.461°. Both pass.

Why 0.219° is small. The solar disc subtends 0.5334°, so the error is 41% of the width of the sun itself. In physical terms it displaces a shadow by 3.8 mm at one metre, while the penumbra cast by the sun's finite disc is already 9.3 mm wide at that distance. The error sits inside the shadow's own soft edge and cannot be seen.

The near-zenith finding

Azimuth error behaves very differently from direction error near the zenith. This matters at tropical latitudes, so it was measured rather than assumed.

Azimuth error grows by more than two orders of magnitude while direction error stays flat. That is the signature of a coordinate singularity rather than a physics error: near the zenith, azimuth swings wildly for a negligible change in actual direction. Singapore's sun exceeds 88° on 20 days of 2026, so this regime is reached in normal use and is documented rather than hidden.

Reproduce it

git clone https://github.com/tjandera/lumos && cd lumos
npm install suncalc@1.9.0
node scripts/validation/sun-vs-noaa.js
node scripts/validation/sun-direction-error.js
What this does not prove. These scripts validate the sun vector, not the rendered image. Confirming that the drawn shadow lands where the real one does requires photographing a room at known times and comparing. That test is planned, not done.
