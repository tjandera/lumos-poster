§3Is the sun in the right place?

The poster claims Lumos' sun never deviates from NOAA's reference model by more than 0.219 degrees. Here is exactly how that number was produced, and what it does and does not mean.

What was compared

Lumos derives sun position from suncalc@1.9.0, called in packages/core/src/sunlight.ts. NOAA's Solar Position Algorithm was re-implemented from the published equations[5] in a standalone script that shares no code with the application. The two were then compared on the quantity the renderer actually consumes: the sun direction vector, after Lumos applies its own azimuth-to-bearing conversion.

Why this is worth doing at all

Both suncalc and NOAA's calculator derive from the same source, Meeus' Astronomical Algorithms[6]. Close agreement is therefore expected. What this measurement establishes is not that the astronomy is right, but that our implementation and our coordinate conversion are right. Those are the parts we wrote, and those are the parts that could silently be wrong.

The algorithm, as implemented

Julian day from a UTC timestamp, then NOAA's chain of terms:

JC   = (JD - 2451545) / 36525                      // Julian century
L0   = 280.46646 + JC(36000.76983 + 0.0003032 JC)  // geometric mean longitude
M    = 357.52911 + JC(35999.05029 - 0.0001537 JC)  // geometric mean anomaly
e    = 0.016708634 - JC(0.000042037 + 0.0000001267 JC)
C    = sin(M)(1.914602 - JC(0.004817 + 0.000014 JC))
     + sin(2M)(0.019993 - 0.000101 JC) + sin(3M)(0.000289)
app  = L0 + C - 0.00569 - 0.00478 sin(125.04 - 1934.136 JC)
obl  = 23.439291... + 0.00256 cos(125.04 - 1934.136 JC)
decl = asin( sin(obl) sin(app) )
y    = tan²(obl / 2)
eqt  = 4 · deg( y sin(2L0) - 2e sin(M) + 4ey sin(M)cos(2L0)
                - 0.5y² sin(4L0) - 1.25e² sin(2M) )
tst  = (UTC_minutes + eqt + 4 · longitude) mod 1440
ha   = tst/4 - 180
zen  = acos( sin(lat)sin(decl) + cos(lat)cos(decl)cos(ha) )
elev = 90 - zen

Neither implementation applies an atmospheric refraction correction, so the comparison is like for like.

The headline number

Maximum direction error is 0.2187°, and it is the same to four decimal places at the equator, at 40°N and at 64°N. An error that is flat across latitude is characteristic of a small constant modelling difference between the two algorithms, not of a latitude-dependent bug in ours.

The near-zenith finding

Azimuth error grows by more than two orders of magnitude near the zenith while direction error stays flat. That is the signature of a coordinate singularity, not a physics error, and it matters at tropical latitudes.

Singapore sits at 1.35°N, so twice a year the sun passes almost directly overhead. As it does, the compass bearing of the sun swings across a large arc for a negligible change in its actual direction. Measured over 2026 at 2-minute resolution:

Above 88° a shadow is shorter than 3.5% of the height of the object casting it, so the compass direction of that shadow is visually irrelevant. This is why the instability is real, reachable in normal use in Singapore, and yet has no visible consequence. We report it rather than hiding it because a reader who checks only the azimuth column would otherwise conclude our sun is broken.

What 0.219° means physically

An angle is not intuitive. Converted into millimetres of shadow, the error is smaller than the blur that is already on every shadow edge.

Against the size of the sun itself

The solar disc subtends a mean angular diameter of 0.5334° seen from Earth. Our worst error is therefore 

0.2187 / 0.5334 = 0.410  →  41.0% of the width of the sun

Shadow displacement

An angular error θ displaces the edge of a shadow by d · tan(θ), where d is the distance from the object to the surface it shadows. The penumbra, the soft edge that exists because the sun is a disc and not a point, has width d · tan(0.5334°).

DistanceDisplacement from our errorPenumbra width already present
0.5 m1.9 mm4.7 mm
1 m3.8 mm9.3 mm
2 m7.6 mm18.6 mm
3 m11.5 mm27.9 mm

At every distance the displacement is smaller than the penumbra. The error falls inside the soft edge the shadow already has, so it cannot be resolved by eye even in principle.

Shadow length, the worst case

Length is more sensitive than displacement when the sun is low, because shadow length goes as h / tan(elevation) and its derivative is h / sin²(elevation). For a 1 m tall object:

The worst case is a low sun, where a 1 m object's shadow is off by 57 mm over 3.7 m. That is 1.5% of the length, and still well inside the penumbra at that distance.

Reproduce all of it

git clone https://github.com/tjandera/lumos && cd lumos
npm install suncalc@1.9.0
node scripts/validation/sun-vs-noaa.js          # elevation and azimuth
node scripts/validation/sun-direction-error.js  # direction vector, near-zenith bands

Both scripts run the self-check first and print every figure on this page. They take about 20 seconds each.

Three caveats on reading this table

  • "Batches fully valid" flatters us. A trial in which every request was refused counts as vacuously clean. Read the 58.0% alongside the 19.1% refusal rate, never on its own.
  • Latency is order-of-magnitude only. The mean varied 6.06 to 1.15 to 1.21 ms across three consecutive runs as the JIT warmed up. Every count-based metric was byte-identical across those same runs.
  • The 14.9% is a real defect, not noise. See below.

The defect this benchmark found

The placer's own documentation states that every emitted placement satisfies every hard constraint. It does not. 14.9% of placements leave a walkway blocked, and all 107 observed violations share one shape.

Root cause. When the placer positions an item it registers that item's footprint as an obstacle for later placements, but not the clear space in front of it. So item N's walkway is validated at the moment N is placed, and item N+1 is then free to land inside it. Nothing revisits N.

Why the unit tests missed it. They check each placement against the room as it stood when that placement was made, which is precisely the blind spot the placer itself has. Only the benchmark's independently written validator, which grades every item against the final batch, could expose it.

We left the defect in and reported it because the measurement is the result. Shipping a quiet fix and a clean 0% would have concealed the most useful thing we learned: a validator that shares its subject's assumptions cannot find this class of bug.

Reproducibility status, stated plainly

The constraint solver is in the repository, including its clearance handling (packages/ai/src/solver.ts, DEFAULT_CLEARANCE, needsFrontClearance, and a describe("clearance") block in solver.test.ts).

The measurement harness that produced the table above is not yet in the public repository. Until it is pushed, these figures are ours to assert and not yet yours to verify. The sun figures in §3 are fully reproducible today.

What we do not claim

Collected in one place, because each of these is a limit a reader could otherwise mistake for a claim.

  • The baseline is uniform-random placement, not a language model. It establishes that these constraints are hard to satisfy by chance. It does not establish that the placer beats an LLM, and no real LLM has been benchmarked.
  • §3 validates the sun vector, not the rendered image. Confirming that a drawn shadow lands where the real one does requires photographing a room at known times and comparing. That test is planned, not done.
  • Time zones and daylight saving are unverified. Sun position is computed from the site's coordinates and a local time, but DST handling has never been checked against reference ephemeris values. In a DST-observing region the shadows could be a full hour out, rendered confidently.
  • The lux targets are design approximations. 100, 150, 300 and 500 lx are targets, not certified compliance values. SS 531[7] covers workplaces, not homes. The code says so itself: the daylight model is described in source as "a plausibility model for a design tool, not a daylight compliance calculation".
  • The test suite is red. 25 tests fail after a module port still in progress, so pnpm test exits non-zero. The features run in the application; the tests point at moved paths.
  • Parts are verified by proxy. The Postgres adapter was exercised against an in-memory emulation and never a live server. Docker images were reviewed by hand, never run.
  • No user study. Zero external users have been observed using this.
